# Fearless

> A TypeScript microframework with a hybrid Rust+Bun runtime. Declarative routes execute in a Rust core at multi-million RPS; function handlers execute on Bun. Both ship in the same deployable unit. The roadmap is to grow the Rust-compiled subset over time so user TypeScript automatically gets faster across releases.

This file is a project map for new contributors (humans or AI agents) coming into the codebase. It is short on purpose. Follow the links to drill in.

## Critical concepts

### Hybrid runtime

A Fearless app runs as **two coordinated processes**:

1. **rust-core (binary).** Owns port 8080. Serves declarative template routes (`app.text`, `app.json`, `app.html`) at multi-million RPS. Handles connection lifecycle, HTTP parsing, pipelining.
2. **Node or Bun (TS).** Owns the rest — function handlers, hooks, JS-side application logic.

When the app has no function handlers, the Rust core can serve everything alone. When the app has function handlers, the dispatcher today routes those to Node/Bun. The [AOT strategy](./docs/superpowers/plans/2026-05-08-aot-strategy.md) describes how function handlers will progressively compile to Rust at build time.

### Routing model

Routes are registered through `App`. The internal `RouteDefinition` is a discriminated union:

```ts
type RouteDefinition =
  | { kind: "template"; method; compiledPath; response: RouteResponseSpec } // Rust-eligible
  | { kind: "handler"; method; compiledPath; handler: Handler };            // Node/Bun
```

`app.get(path, ctx => ...)` registers a `handler`. `app.json(path, body)` registers a `template`. Mix freely. If any route is a `handler`, the app cannot use the Rust runtime (templates can still be served by Node/Bun in fallback mode).

### Ctx — the handler argument

`Ctx` is the single object passed to every handler and hook. Defined in [`src/types.ts`](./src/types.ts). Implementation in [`src/ctx.ts`](./src/ctx.ts) (`RequestContext` class with `fromNode` and `fromWeb` factories). API surface intentionally small:

- inputs: `method, path, url, params, query, headers, ip, state`
- body: `body<T>(), text(), formData(), validate(fn)`
- response builders: `json(), html(), raw(), redirect(), notFound(), noContent()`
- chainable: `status(), header(), setHeaders()`

### Hook pipeline

Three lifecycle points run by [`HookChain`](./src/middleware.ts) around every handler:

1. `onRequest` — runs before the handler. Returning a `Response` short-circuits.
2. handler runs.
3. `onResponse` — can replace the response.
4. `onError` — runs only if anything in 1-3 throws. Can recover with a `Response`. If all error hooks return undefined, default 500 fallback (or `HttpError.toResponse` if the thrown error was an `HttpError`).

### Rust core entry points

- `run_server(manifest, port)` — generic dynamic dispatch through the `RouteTable`. Used when the manifest has non-benchmark routes.
- `run_benchmark_server(port)` — optimized dispatch for `/plaintext` + `/json`. On Linux+`io-uring` feature, this path uses the multi-thread io_uring runtime under [`src/uring/`](./rust-core/src/uring/).
- `main.rs` auto-detects which path to use based on the loaded manifest shape.

## Common commands

```bash
# JS / TS
npm install                  # install deps
npm run build                # tsc -> dist/
npm run dev                  # tsx watch examples/basic.ts
npm test                     # JS tests + Rust check
npm run test:js              # JS tests only
npm run lint                 # oxlint report
npm run lint:fix             # oxlint autofix safe rules
npm run bench:micro          # tinybench JS micro-benches
npm run bench:tfb            # full TFB harness run

# Rust
cargo build --release --manifest-path rust-core/Cargo.toml
cargo build --release --manifest-path rust-core/Cargo.toml --features io-uring
cargo test --manifest-path rust-core/Cargo.toml
cargo bench --manifest-path rust-core/Cargo.toml

# End-to-end (local Linux via OrbStack)
docker build -f bench/techempower/fearless-rust.dockerfile -t fearless-rust:test .
docker run -d --name fearless-bench \
  --ulimit memlock=-1 --cap-add SYS_NICE \
  --security-opt seccomp=unconfined \
  -e FEARLESS_SQPOLL_MS=0 \
  -p 8080:8080 fearless-rust:test
```

## Coding rules

The full rule set lives in [`AGENTS.md`](./AGENTS.md). A non-exhaustive condensation:

- Public API stays small. Adding to `src/index.ts` is a real decision.
- Hot path (Rust + TS dispatcher) avoids allocations, per-request work, and unnecessary abstractions.
- Validation is pluggable. Do not bind to a specific schema library in core.
- New built-ins must be tiny and dependency-light. `cors()` and `securityHeaders()` are the existing examples.
- TypeScript code aims to be AOT-compatible (no `any`, prefer `const`, no closures over mutable state, no dynamic property access). The optional `oxlint` config is the day-to-day enforcer.
- Rust changes that touch the request hot path require a benchmark before/after.
- Conventional commits with scopes: `feat(rust-core)`, `perf(rust-core)`, `fix(ts)`, `docs`, `test`, `chore`.

## When in doubt

- Read [`AGENTS.md`](./AGENTS.md).
- Read the relevant strategy doc under [`docs/superpowers/plans/`](./docs/superpowers/plans/).
- Run the existing tests before changing anything (`npm test`, `cargo test`).
- Prefer a small PR that lands cleanly over a big PR with regressions. Multi-step changes get split into commits per the discriminated step (see recent git history for examples — Phase 0/1/2/3/4 of the io_uring sprint each landed as multiple small commits).
